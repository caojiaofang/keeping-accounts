# 墨记：多人账本需求与实施说明

记录日期：2026-10-24。

用户希望邀请爱人、家人等多人使用同一本账本，进行家庭共同记账。每个人使用自己的微信身份，所有有效成员可以查看共同账本的收支、日历和统计。

## 1. 当前实现与体验模式

真实共享账本已完成前后端实现，开发库及正式库均已应用 `0004_shared`，通过真实数据库闭环与并发权限测试。已接入创建、邀请预览/接受/撤销、成员管理、共同账单、修改记录及退出/转让/解散；具体 API 和配置见[共享账本说明](../backend/docs/shared-books.md)。正式服务已更新至 `20261025T043611Z`，小程序体验版 `1.0.9` 已发布；2026-10-26 用户确认双账号真机测试已完成。

未登录体验模式保留原有本地交互，可从「我的账本 → 多人账本」进入：

- 创建多人账本，创建人为当前演示用户「我」。
- 主动体验家庭示例：两位演示成员和三笔共同收支；已有个人「小家账本」不自动变为共享账本。
- 体验示例邀请，确认后以普通成员加入独立的演示账本；重复打开不重复加入或生成示例账单。
- 查看共同收支、每位成员记录的支出和笔数，按成员筛选明细；移出成员的历史记录仍可查看。
- 共同明细和消费日历展示记账人，新增账单自动归属当前演示身份，编辑账单保留原记账人。
- 从「我的」导出当前共同账本时，CSV 同时保留记账人。
- 创建者管理成员、维护共同账单和预算；普通成员查看共同账单并维护自己的账单；共同账单不能跨账本转移。
- 创建者预览、重新生成或撤销七天有效的本机演示邀请；移出成员时撤销该账本已有邀请。
- 成员、邀请和记账人信息保存在原有本地存储，兼容没有这些字段的旧数据。

体验页面明确提示不能跨设备邀请或同步，不调用微信分享接口。登录后使用真实后端邀请和微信分享入口，演示中的家人不会成为实际成员。微信登录已接入，见[微信登录需求](微信登录需求.md)。

## 2. 正式使用流程

1. 用户微信登录，由后端确定内部用户 ID。
2. 创建「多人账本」，后端在同一事务中创建账本和创建者成员关系。
3. 创建者点击「邀请成员」，后端生成带有效期、可撤销的邀请；小程序将邀请页面作为微信分享卡片发给对方。
4. 对方打开后可先查看邀请者、账本名称、加入后的可见范围；加入前不能查看实际收支、成员详情或统计。
5. 对方登录并明确确认加入，后端再次验证邀请、账本状态及成员关系，在事务中建立成员关系。仅打开分享页面不会自动加入。
6. 成员各自记账，记录归入同一账本；后端保存成功后刷新共同明细、统计、预算使用情况和日历。

「共同收入」为成员在该账本记录的收入，不表示成员全部个人收入；「记账人」是提交记录的人，不等同于实际付款人。本期不包含 AA 分账、债务结算、家庭资金余额或支付功能。

## 3. 首版权限

| 操作 | 创建者 | 普通成员 | 非成员或已退出成员 |
| --- | --- | --- | --- |
| 查看共同明细、成员、日历及统计 | 可以 | 可以 | 不可以 |
| 新增共同账单 | 可以 | 可以，以本人作为记账人 | 不可以 |
| 修改、删除本人账单 | 可以 | 可以 | 不可以 |
| 修改、删除其他成员账单 | 可以，保留原记账人和修改记录 | 不可以 | 不可以 |
| 设置共同预算、管理成员与邀请 | 可以 | 不可以 | 不可以 |
| 查询、导出共同账单及 AI 分析 | 可以 | 可以，仅限当前有权限的共同账本 | 不可以 |

个人账本继续仅属于本人，不能因为双方共同使用一本账本，就访问彼此其他个人账本。邀请不会把创建者的旧个人账单自动带入共同账本。

普通成员退出、创建者转让及解散账本已在真实后端及登录页面实现，本地体验仍只支持创建者移出其他普通成员。创建者不能直接移出自己；转让或解散有独立确认流程。成员被移出或退出后立即失去后端读取和写入权限，其历史账单及原记账人保留。

## 4. 后端数据与接口约定

后端沿用 Python + FastAPI + PostgreSQL + Redis，不另设服务。已实现以下模型：

| 数据 | 核心字段与约束 |
| --- | --- |
| 账本 | `id`、`kind`、`owner_id`、名称、预算、状态、版本 |
| 成员关系 | `book_id`、`user_id`、角色、状态、加入与退出时间；`(book_id, user_id)` 唯一，避免并发重复加入 |
| 邀请 | 邀请凭证摘要、`book_id`、邀请者、到期时间、撤销状态及接受记录 |
| 账单 | `book_id`、`created_by`、`updated_by`、金额（整数分）、版本和创建/更新时间 |
| 修改记录 | 操作人、目标账单、操作时间及变更内容，用于解释共同账单的修改 |

接口以 `/api/v1/books` 为业务入口；公开预览和登录接受邀请使用 `/api/v1/book-invitations`。准确路径、请求与返回结构见[共享账本说明](../backend/docs/shared-books.md)及开发后端 OpenAPI。

- 当前用户始终从后端登录态解析。前端不能通过传入 `created_by`、OpenID 或创建者 ID 指定操作身份。
- 所有账单、成员、日历、统计、导出和 AI 工具查询先验证成员关系；不允许仅通过猜测账本 ID 读取数据。
- 邀请使用随机 UUID 与专用密钥签名的不可预测凭证，后端只保存摘要，并绑定应用及环境；有效期为七天，过期、撤销或轮换密钥后不能加入。演示中的 `demo-` 标识不能作为正式凭证。
- 首版可重复分享同一邀请，允许多位家人分别确认加入。创建者可随时撤销；重新生成时旧邀请失效；移出成员时撤销现有邀请，重新邀请需要生成新凭证并显式确认。
- 验证邀请与建立成员关系在同一事务中处理；重复确认返回已有成员状态，不重复建成员。并发加入、邀请撤销和成员移出需通过事务及约束处理竞争条件。
- 修改他人账单、移出成员、退出和解散等操作必须在服务端校验权限。成员失效后，其旧登录凭证也不能继续操作该账本；如缓存权限，成员变化时同步使缓存失效。
- 多设备编辑同一账单使用版本号检查；出现冲突时提示刷新，不静默覆盖他人的更改。
- 正式版通过进入页面、保存成功后刷新和下拉刷新获取最新数据；是否增加实时推送在后续确定。未收到后端保存成功前不展示为已同步，网络失败提供明确重试且避免重复记账。
- PostgreSQL 保存成员、账单和邀请等正式状态，Redis 可辅助限流和短期状态，不能成为长期账单或权限关系的唯一来源。
- 开发环境使用 `keeping_accounts_dev`、`moji:dev:`，正式环境使用 `keeping_accounts_prod`、`moji:prod:`。

## 5. 正式联调验收

1. 两个真实微信账号接受同一邀请后能查看同一账本，各自新增记录可在刷新后被对方看到。
2. 同一用户重复加入、重试保存不会产生重复成员或账单。
3. 普通成员不能修改他人账单、设置预算或管理邀请，直接请求后端也不能绕过限制。
4. 创建者修改他人账单时保留原记账人，能识别最后修改人。
5. 被移出的成员不能再访问共同数据；原有记录和统计保留，旧邀请不能用于重新加入。
6. 非成员、个人账本、其他家庭账本之间相互隔离，AI 分析和导出遵循同一权限。
7. 过期、撤销、伪造邀请与旧环境邀请不能加入账本；打开邀请页面不自动建立成员关系。
8. 账单按当前账本正确汇总，按成员查看不会漏掉已移出成员的历史记录。
9. 多设备冲突、断网重试和登录失效都有明确反馈，不把失败写入展示为成功同步。
10. 演示数据不自动上传；后端接入时提供明确的演示与真实数据边界。
