## 2. 产品目标与现状

目标：让用户围绕当前账本自然地查账、追问、比较、理解消费变化，并进一步制定可计算的预算方案。

现在已具备：按月分类汇总、明细、大额收支、前月比较、消费建议、云端历史、SSE 流式回答、个人及共享账本权限、失败重试与消息幂等。

主要限制：

- 查询计划只支持固定操作和单个自然月，缺少任意日期、备注搜索及组合筛选。
- 一轮基本只执行一种统计，难以连续查询后回答“为什么多花了”。
- 上下文主要是月份、单分类、收支类型和最近六条问题，缺少先前回答、结果引用及筛选修正。
- 回答主要使用一种统计卡，后续建议问题固定，账单结果缺少可操作的关联入口。
- 已有预算字段，但未形成预算分析、情景计算和可管理的长期偏好。

保留现有技术栈：uni-app、Vue 3、TypeScript、Pinia、FastAPI、PostgreSQL、Redis 和 sub2api。先复用现有模型配置，不以更换模型作为升级前提。当前 `xhigh` 配置若需调整，单独评估和记录。

“主动”第一版体现为在回答中发现值得继续看的变化，并给出相关追问；自动生成周报、定时提醒等另立需求。

## 4. 核心功能与统一口径

### 4.1 自然语言查账

支持今天、昨天、本周、上周、最近 N 天、本月、上月、今年及明确起止日期。时区固定为 `Asia/Shanghai`，由后端提供可信日期。

- “最近七天”包含今天，共七个自然日；本周从周一开始，截至今天。
- 本月、今年默认截至今天；历史完整周期按完整周期查询。
- “国庆出去玩”这类表达需要明确日期及匹配条件；不能把该期间所有支出直接认定为旅行消费。
- “上次买耳机”先按关键词查找，默认回溯范围和扩大范围入口需要展示；零结果只说明当前检索范围内未找到。
- 支持收支类型、多个分类、备注关键词、金额上下限、账户、共享账本记账人及排除条件组合使用。
- 账户目前是账单上的文本字段，按实际保存值筛选，不假定存在独立银行账户或余额系统。
- 共享账本成员按账单 `createdBy` 统计，文案使用“记账人”。不把录入者自动认定为实际付款人或消费受益人。
- “奶茶”“外卖”先采用可解释的关键词及同义词规则；不能把整个餐饮或咖啡茶饮分类当作精确匹配。结果显示匹配依据，支持用户纠正。

### 4.2 多步分析与追问

- 一轮可以先汇总、再对比、再查看明细，按实际需要停止查询。
- 支持“咖啡也算上”“排除这笔”“只看周末”“换成上周”“按记账人分开”等上下文修改。
- 记住的是经过校验的筛选条件、相关回答摘要和结果引用；每轮重新查询有效账单，不把历史快照当作最新数据。
- “为什么多花了”回答可解释的差额来源，例如分类差额及相关账单；账单没有描述原因时，不编造生活事件。
- 多个筛选对象或多笔相近账单无法确定时，先给候选或提一个明确的补充问题。

### 4.3 数据可信与计算规则

- 金额统一使用整数分；总额、笔数、比例、差额和测算由后端计算。
- 保留权限隔离、有效记录过滤、幂等、会话并发保护，以及保存前再次验证权限。
- 查询用户和账本由后端绑定，模型不能指定任意身份、跨账本访问或生成 SQL。
- 退款目前是独立收入分类，不自动抵扣支出；展示净收支时说明口径。
- 同期比较默认使用可比区间，并展示两段实际日期；用户明确要求完整周期时遵从并说明差异。
- 基期为零时不输出增长百分比；“没有记录”不能解释为实际没有消费。
- 差额归因只说明账单数值上的贡献，不等同于现实因果。一次性支出由备注或用户明确标记，不能仅凭金额大而认定。
- 明细分页与汇总分开处理：展示二十笔不代表只统计二十笔，排除“这笔”必须对应真实账单 ID。
- 同一张统计卡内部数据保持一致；跨工具查询如遇并发修改，重新读取关键统计或提示更新时间，不用长事务跨越模型等待。
- 模型正文中的数值继续通过后端事实引用替换与校验。新增差额、预算、测算结果同样进入事实集合。

### 4.4 示例对话

以下为目标行为，具体金额以实际账单计算为准。

| 对话 | 预期行为 |
| --- | --- |
| “最近七天花了多少？”→“和之前七天比呢？” | 比较相邻两个七天区间，保留收支与其他筛选 |
| “奶茶花多少？”→“咖啡也算上” | 扩展关键词范围，去重后重新统计，并显示匹配依据 |
| “本月怎么花得这么快？”→“排除这笔再看看” | 查询差额来源，引用具体账单后排除该 ID，重算两期结果 |
| “上次买耳机是哪笔？”→“打开看看” | 搜索候选，展示真实账单入口，打开时重新核对可访问性 |
| “家里这个月谁记得最多？” | 按共享账本记账人汇总，不称为实际消费最多的人 |
| “房租不能动，想少花五百” | 第二版结合用户约束计算可调整方案，不保证一定能实现 |

## 5. 技术实现方向

流程：用户问题 → 读取受控上下文 → 模型选择查询工具 → 后端校验和执行 → 返回结构化事实 → 按需继续查询 → 生成可校验回答、结果卡及追问 → 原子保存完整轮次。

采用一个助手和有限工具循环，先不引入多智能体框架或向量数据库。现有 `LlmClient` 提供结构化生成和流式正文，尚不能据此认定原生 tool calling 已可用；须先验证实际 sub2api 链路。

优先使用验证通过的原生工具调用；若上游不支持，则用现有严格结构化输出表达“调用工具或结束”，由后端执行同样的循环。两种方式共享工具参数、权限和结果结构，不退回只能选一次固定分析的旧流程。

工具边界如下，第 01 步已固定第一版契约，详见[接口与模型接入契约](../backend/docs/chat-assistant-v2.md)：

| 工具 | 职责 |
| --- | --- |
| `summarize_entries` | 范围内收支汇总，按分类、日期、账户或记账人分组 |
| `search_entries` | 按筛选检索账单，稳定分页，返回真实 ID 和匹配依据 |
| `compare_periods` | 两个明确区间的总额、分类差额及可比较口径 |
| `get_entry` | 读取有权访问的单笔账单，支持“这笔”及详情入口 |
| `get_budget_status` | 第二版读取现有预算并计算使用情况 |
| `calculate_scenario` | 第二版执行后端支持的情景公式，返回假设和结果 |

初始限制建议：单轮最多六次工具调用、最多六次模型请求、明细每页二十笔，单次日期跨度最多三百六十六天；均需配置化和测试。达到限制时返回已验证的部分结果或请用户缩小问题，不无限循环。限制值在真实验收后调整，整轮仍受统一超时预算约束。

### 5.1 数据与接口演进

- 使用独立的 V2 路由承载新结构，建议前缀 `/api/v1/assistant/v2`；旧接口和原有消息返回结构继续保留。
- V2 会话按账号和账本读取历史，入口月份仅为默认范围，不再限制后续查询或历史检索。
- 新上下文至少描述日期区间、收支、分类集合、关键词、账户、记账人、排除 ID、比较区间，以及最近结果引用；区分“用户明确指定”和“默认继承”。
- 消息结果增加 `schemaVersion`、`cards`、`suggestions`、`factRefs` 及必要的完整性状态。卡片携带类型、稳定 ID、查询范围和生成时间。
- 卡片类型至少包括汇总、账单列表、趋势、差额分析；第二版增加预算和测算。
- 历史消息保留生成时快照，新轮查询最新数据。旧会话转换、读写路由及客户端回退方式在第 01、07 步明确。
- SSE 沿用现有进度、快照、正文、完成和错误语义，V2 快照定义为当前轮的完整预览，后续快照替换前一次，避免重复追加卡片。`done` 仍代表完整轮次已保存。
- 仅保留模型需要的摘要和必要明细，不上传全量账单、OpenID、token 或模型推理。日志记录工具类型、耗时和结果规模，默认不记录账单备注及完整聊天正文。
- 原始问答继续保存；长对话摘要附带覆盖序号，不覆盖原始历史。账单引用是定位依据，不是绕过权限的授权凭据。

依赖：01。状态：已完成，2026-10-28。实现规则、调用方式和验证见[日期与组合筛选](../backend/docs/chat-v2-filters.md)。

### 第 03 步：完成查账工具与结构化事实

依赖：02。状态：已完成，2026-10-28。实现和验证见[只读查账工具与事实输出](../backend/docs/chat-v2-tools.md)。

- 实现第一版四个只读工具：汇总、搜索、比较、单笔读取。
- 搜索返回真实账单 ID、匹配依据、排序与分页信息；汇总覆盖全部匹配记录。
- 比较工具计算绝对差额、可用时的比例及分类贡献，支持负贡献，不夸大归因。
- 为工具结果建立稳定事实引用，包含单位、日期范围及数据生成时间。

主要范围：后端工具注册、查询服务、schema 和测试。

验收：构造同一套账单，核对搜索、汇总、分类贡献的金额一致；覆盖超过二十笔、同日同金额分页、退款、基期为零、被删除记录与账号/账本隔离。

### 第 04 步：实现可修正的对话上下文

依赖：03。状态：已完成，2026-11-04。实现、保存策略和验证见[可修正的对话上下文](../backend/docs/chat-v2-context.md)。

- 保存并恢复完整筛选、比较范围、先前回答摘要及结果引用。
- 支持增加、替换、清空条件，明确“咖啡也算上”和“换成咖啡”的不同含义。
- 处理“这笔”“这些”“还是刚才那类”等引用；引用不唯一时返回候选。
- 设置上下文长度预算及长对话摘要规则；旧会话只有月份和单分类时可转换读取。

主要范围：V2 上下文服务、会话持久化、模型输入组装及迁移（如需要）。

验收：至少覆盖连续五轮的条件变更；重开会话后仍能恢复范围；切换账号或账本不继承旧引用；账单更新后，新轮重新读取；失败轮次不覆盖成功上下文。

### 第 05 步：实现有边界的多步工具循环

依赖：03、04，以及第 01 步确定的模型调用方案。状态：已完成，2026-11-04。实现及验证见[有边界的多步工具循环](../backend/docs/chat-v2-loop.md)。

- 模型根据问题选择工具，读取结果后决定继续查、补充询问或结束回答。
- 校验工具名称和参数，绑定当前身份及账本；工具结果和备注均作为数据处理。
- 增加调用次数、输出规模、整轮超时及重复查询保护，取消时终止后续上游请求。
- 有部分结果时可明确降级；没有事实时不生成消费结论。暂时性故障不得伪装成“没有记录”。

主要范围：V2 助手编排服务、模型适配、限额配置和测试。

验收：模拟“本月为什么多花了”能够依次查汇总、对比、必要明细；简单问题不强制执行全套查询；覆盖非法工具、重复调用、预算耗尽、断流、模型失败和注入式备注。

### 第 06 步：生成可信回答与动态追问

依赖：05。状态：已完成，2026-11-04。实现规则、接入方式和验证见[可信回答与动态追问](../backend/docs/chat-v2-answer.md)。

- 先回答用户的问题，再按需展示证据，不强制每次附带同一张大卡片。
- 支持多个工具事实的引用替换及正文数值校验，沿用已有防止虚构数字的原则。
- 生成与本轮结果有关的二至三个追问，附带受控上下文引用，例如“排除这笔再比较”。
- 区分已验证事实、可解释的差额贡献和条件性估算；无上期数据时明确说明。
