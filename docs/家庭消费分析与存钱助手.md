# 聊聊花费：家庭消费分析与存钱助手

2026-11-25，「聊聊花费」已恢复为原有账单问答，本文保留此前的设计、实施与发布记录。

日期：2026-11-16。作为原[智能助手开发计划](聊聊花费智能助手开发计划.md)第二版的细化方案，核心流程完成开发，后端随后发布。此前的接口与验证见[实现说明](../backend/docs/savings-assistant.md)。

## 1. 产品目标

帮助家庭根据真实账单理解钱花在哪里，找出可以避免或降低的支出，安排下月收入用途，跟踪执行并逐步存下钱。

核心体验是“家庭消费体检 → 确认可调整项 → 制定下月存钱计划 → 月中关注 → 月末复盘”。自然语言查账作为基础能力保留，用户不必先提出专业问题才能获得分析。

是否成功，主要看建议是否有依据、是否可执行，以及执行后家庭结余和已确认存款的变化。消息数量或统计图数量不作为主要成果。

## 2. 当前实现与缺口

核对代码后的现状：

- `backend/app/services/chat_v2_loop.py` 支持汇总、比较、明细和单笔查询，模型最终主要返回事实引用。
- `backend/app/services/chat_v2_answer.py` 使用服务端固定模板组织回答。金额校验已具备，但还没有消费诊断、家庭收入分配和存钱建议的语义结构。
- `backend/app/services/chat_v2_suggestions.py` 的追问集中在明细、分类、比较和排除账单，尚未形成行动与复盘。
- `frontend/components/assistant/ExpenseChat.vue` 以聊天和结果卡为主，缺少家庭体检、存钱目标及本月行动入口。
- 已有独立月预算及账单关联，可读取当月项目、额度、已用、剩余和未关联支出。家庭目标和旧资金记录虽有部分基础结构，不能据此认为当前聊天已接入存钱规划。

因此需要新增产品流程、分析事实、家庭约束和计划状态，不能只放开模型自由回答或更换入口文案。

## 3. 用户看到的功能

### 3.1 家庭消费体检

入口提供“分析家庭消费”“找出下月可减少的花费”“制定下月存钱计划”“看看本月执行情况”。

默认分析当前账本，以近期最多三个完整月份建立参考，本月按截至今天的数据单独展示。样本不足时使用实际已有范围并说明，不强制要求用户凑齐历史。

报告先给最相关的结论，再展示依据和建议：

- 已记录收入、支出、账面结余，以及数据缺口。
- 主要支出和变化来源，区分消费次数增加、平均单笔变化与一次性大额支出。
- 优先查看的少量可调整项，每项可展开真实账单和匹配依据。
- 下月需要预留的费用与可能影响存钱目标的事项。

一次性、固定或必要支出应来自账单明确内容或用户确认；不能仅凭分类、金额或出现频率认定。

### 3.2 找出可能可以避免的消费

分析候选包括频繁小额购买、可替代的便利性消费、待确认是否仍使用的订阅、可能重复的购买，以及用户自己希望压缩的消费。

每条建议至少包含：

| 内容 | 示例含义 |
| --- | --- |
| 发现 | 某类备注匹配的消费频率上升 |
| 依据 | 实际日期、金额、笔数、账单引用和匹配方式 |
| 判断前提 | 是否为工作需要、家庭必要开支或一次性购买，哪些信息尚待确认 |
| 具体行动 | 减少次数、设置额度、替换部分购买或核对订阅用途 |
| 节省测算 | 采用什么基准、假设减少多少、测算周期及对应结果 |
| 用户反馈 | “可以减少”“这是必要支出”“只是一次性”“判断不准确” |

高支出不等于浪费。医疗、教育、住房等也不能仅按分类判断可削减或不可削减，应尊重家庭实际约束；不对成员进行浪费排名。

模型负责归纳与提出候选，事实由后端计算。无法确认用途时使用“值得核对”“可能可以减少”等表达，反馈后更新建议，避免每月重复劝用户削减已确认的必要开支。

### 3.3 家庭收入分配与存钱计划

首次制定计划时，优先从账单和现有预算提取信息，只补问影响方案的关键缺口：

- 下月可支配收入及稳定程度；历史收入仅作参考，未到账收入不能当作现有余额。
- 希望存下的金额，或希望达到的目标与期限。
- 不可调整的开支、还款义务、基本生活需要和近期大额事项。
- 愿意调整的消费，以及不希望压缩的项目。

计划将预计可支配收入安排到必要支出、可调整支出、近期费用预留、机动金额及计划存下金额。已知还款等义务必须纳入，具体归类保持一致。

基本校验：预计收入 = 计划支出 + 预留 + 机动金额 + 计划存下金额。支出项目和预留不得重复计算；收入不足时显示缺口，不生成负的生活预算以凑够目标。

给出可调整方案及其差异，而非强制采用统一收入比例。用户改变“房租不能动”“外卖最多减少一半”等条件时，重新计算；目标不可达时说明缺口和可选调整。

当前月预算继续独立使用，不强制要求所有用户填写收入。存钱助手读取预算，并在用户选定方案后提供可预览、可编辑的月预算草稿。

### 3.4 下个月记住并跟进

计划保存后，跨会话保留目标、已选行动、适用月份和用户确认的约束。个人想法与家庭共同方案分开保存，共同方案的修改沿用账本业务权限和版本保护。

- 新月进入助手时，主动展示上月待关注事项，读取最新账单后再给建议。
- 月中查看已选行动是否偏离，结合尚未发生的固定开支说明影响，给出可以采取的调整。
- 月末对比计划和实际，记录哪些行动有效、哪些不合适，并生成可修改的下月草稿。
- 没有减少消费也可据实说明，避免把用户没有执行描述为已完成。

第一阶段的“主动”发生在用户进入助手或打开计划时。离线定时推送属于后续能力，需要单独设计通知渠道和订阅；保存计划不代表已设置推送。

## 4. 金额与结论口径

- 金额用整数分计算，金额、比例、次数、情景结果和差额均具有后端事实引用。
- 账面结余是已记录收入减已记录支出，不代表银行余额或实际存下的钱。实际存下金额单独由有效存入记录或用户明确确认支持。
- “可节省金额”是有前提的情景结果，不是保证，也不等于本月已实现的节省。
- 多项行动命中同一账单时去重，并处理互斥或部分重叠方案，不能把同一笔支出削减两遍。
- 退款按现有独立收入口径展示，不当作稳定收入；借款、账户转移等遇到识别不清时先核对，不默认作为可持续家庭收入。
- 订阅、重复购买等只能在数据能支持时提出候选；相似账单不能自动删除，不能仅凭备注认定家庭不需要该消费。
- 尚未结束月份与历史月份采用可比区间；不能机械按日期线性外推房租、工资等集中发生的收支。
- 收入缺失、部分家庭消费未记录、账本仅覆盖部分成员或范围时，明确结果只覆盖现有记录，并允许用户补充。
- 共享账本的记账人不是付款人或受益人；家庭统计不据此判断谁应该少花钱。
- 本月末分析使用最新有效记录，旧报告保留生成时间和历史快照属性；失去权限后不能继续使用原引用获取数据。

## 5. 回答方式与交互

回答按“发现 → 依据 → 建议 → 情景测算 → 下一步”组织。简单查账继续直接给答案，消费分析才展开诊断，避免每个问题都返回长篇报告。

每轮先突出最值得处理的一至三件事。追问围绕实际任务，例如“这项需要保留吗”“按这个方案下月能存多少”“加入下月关注”，不止提供继续查询的按钮。

技术上保留现有事实校验，并扩展结构化分析结果：事实引用、观察、判断前提、不确定性、行动、测算引用。需要校验引用是否真正支持结论，而不仅是检查数字是否存在。模型生成的诊断可以自然表达，但不能把推测保存成家庭事实。

新增消费诊断、收入分配、行动计划和复盘的卡片及协议兼容定义。历史卡片照常展示，不能给现有卡片类型塞入不兼容结构。

## 6. 分步落地

以下为原第 12—14 步的细化顺序，各阶段均需前后端可用和相应验证，不把方案完成标为功能完成。

| 阶段 | 交付 | 核心验收 |
| --- | --- | --- |
| 12-A | 固定分析、测算与卡片契约，读取现有独立月预算 | 收入缺失、未关联支出、月预算为零、已删除预算均有正确口径；旧查询兼容 |
| 13-A | 家庭目标、必要开支和约束的最小可管理记录 | 能保存、修改、停用；个人与家庭范围明确，跨会话恢复且权限隔离 |
| 12-B | 家庭消费体检与可调整消费诊断 | 每条建议可追到账单；错误判断可纠正；样本不足不伪造结论 |
| 12-C | 收入分配与情景测算 | 分配守恒；不重复计算节省；必要开支受保护；不可达目标显示缺口 |
| 13-B / 14-A | 保存选定行动并预览月预算草稿 | 用户可编辑和取消；确认后按现有业务接口及权限写入；重复请求不重复保存 |
| 14-B | 新月关注、月中跟进及月末复盘 | 使用最新账单；区分预计、计划和实际；下月可沿用、调整或停用 |

原第 13 步的最小目标记录提前到测算前，以支持已确认的家庭约束；完整偏好管理继续分步交付。原第 11 步尚未完成的设备验收继续保留，不因方案调整视作已完成。

测试场景至少覆盖：普通家庭、收入未记录、收入不稳定、必要支出较高、一次性大额支出、退款、重复候选、账单不足、月中分析、多个节省行动重叠、用户纠正、共享成员权限变化和新月重新分析。真实模型效果需单独评测，不能仅用固定模板或单元测试代替。
