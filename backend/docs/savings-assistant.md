## 使用流程

1. 消费体检默认读取入口月份和之前最多三个完整月。展示截至当天的收支与账面结余，选择最近一个有支出的完整月作为规划参考；没有完整月时仅使用已有记录，不外推整月。
2. 在「目标与必要开支」确认预计收入、存钱目标、收入稳定程度、保留的分类及文字约束。共享账本默认使用家庭共同方案，也可切为仅自己可见的个人想法。
3. 点击智能分析，由现有模型结合问题和家庭情况选出至多三项优先核对的消费。服务端验证候选和观察是否与账单事实一致，金额不由模型生成；模型不可用时保留账单事实并明确提示。
4. 展开候选可查看最近五笔真实账单，合计和笔数覆盖全部匹配记录。可以标记必要、一次性、判断不准确或可以调整；被保留的项目不再推荐削减，标记可以在偏好中移除。
5. 根据消费建立可编辑方案，填写下月收入、支出、近期预留、机动金额和目标；选中的消费可填写下月上限。也可保留必要支出，让助手按目标和原额度比例试拟可调整项目的分配，采用最大余数法保证整数分守恒；建议可填回项目继续编辑。测算后显示计划存下、未分配金额、生活费用缺口及目标缺口，确认后才保存。
6. 跟进复盘读取最新有效账单，对照分类预算及已选行动。计划存款和用户确认的实际存款分别展示，可以修正实际存款、停用计划、修改本月或未来方案、沿用到下月。
7. 已保存的支出方案可以预览并写入独立月预算；用户能看到替换前总额和全部新项目，可取消或返回编辑。预留、机动及储蓄不写成消费预算，原账单保留。

## 接口与兼容

接口位于 `/api/v1/assistant/v2/savings`，需要登录且 `CHAT_V2_ENABLED=true`，响应均为 `Cache-Control: no-store`。新增工作区使用独立 `schemaVersion=1` 契约，不修改历史 V1/V2 聊天卡片或旧会话。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/workspace?bookId=…&scope=household` | 读取目标、标记及最近 24 份月计划 |
| GET | `/report?bookId=…&scope=…&month=YYYY-MM` | 读取完整聚合、预算及消费候选，不调用模型 |
| POST | `/analyze` | 在报告基础上结合问题选择分析重点，沿用聊天账号限流 |
| POST | `/profile` | 保存目标和约束，校验工作区版本 |
| POST | `/feedback` | 保存或清除对具体消费对象的判断 |
| POST | `/scenario` | 只测算，不保存 |
| POST | `/propose` | 保留必要项目，按目标试拟可编辑分配，不保存 |
| POST | `/plan` | 保存、修改、启停计划及修正确认存款 |
| GET | `/progress?bookId=…&scope=…&month=YYYY-MM` | 读取指定计划的实时执行和复盘 |
| POST | `/budget` | 明确确认后将计划支出写入独立月预算 |

请求和响应的 JSON 使用 camelCase。可执行写入契约位于 `app/schemas/savings.py`，前端类型位于 `frontend/common/types/savings.ts`。金额为整数分，拒绝布尔、浮点及数字字符串；分析与测算结果附后端 `factRefs`，消费候选的 `factIds` 可定位实际金额、笔数及平均单笔。

`scope=personal` 的存储键由服务端绑定当前账号，客户端不能指定其他用户。`household` 按当前账本共享，沿用有效成员共同维护月预算的权限。所有读写先验证当前账本权限；写入持有账本排他锁，并使用版本及固定请求 ID。原 ID 换正文返回 409；成员失权后不能读取或重放旧请求。

目标、反馈和计划分别持久化至 `savings_workspaces`、`savings_plans`；幂等响应保存至 `savings_mutations`。迁移为 `0011_savings_assistant`，父版本为 `0010_book_categories`。月预算导出与预算自身修改记录在同一事务中提交；导出请求成功后，即使存钱计划已更新，原请求仍返回原结果，不重新覆盖预算。

原月预算保存方法新增内部 `commit=False` 组合事务选项，默认行为不变。前端不缓存云端家庭数据；账号、账本或范围切换立即清空状态，并忽略迟到响应。写入结果不确定时保留冻结正文及请求 ID，允许原请求重试；切换输入后旧测算不能重新生效。

## 分析和测算口径

- 消费候选按「分类 + 去首尾空白、不区分大小写的完整备注」聚合，最多返回十二项，默认先展示三项。当前不自动合并不同备注或推断同一商家；同样的备注不等于无用或重复记账。
- 频率观察要求至少三笔；会员/订阅观察要求备注有对应线索；高占比观察使用参考月合计；增长观察要求可比较的两个完整月均有该对象记录。不据此编造生活原因或保证节省。
- 必要分类及“必要、一次性、不准确”反馈由后端排除。文字约束供模型选择重点；需要严格保留的支出应使用必要分类或必要支出标记。
- 情景节省为参考消费减用户选定上限。每个对象只计算一次；含行动的分类须保留原参考总额，避免手动调低后再扣一次。同一分类不能重复安排，必要项目不接受削减行动。
- 收入 = 计划支出 + 预留 + 机动 + 计划存下 + 未分配金额；收入不足时另列费用缺口。存钱目标无法实现时明确显示缺口，不产生负的生活预算。
- 历史收入不自动成为未来收入；收入缺失会提示补充。退款仍按现有独立收入规则展示。账面结余不代表银行余额，预计节省不代表实际存款。
- 执行按明确选择的分类和完整备注匹配。自定义无分类项目需要人工核对，未匹配支出单独显示；不通过记账人推断付款人、受益人或谁浪费钱。
- 修正确认存款或启停计划时保留原方案快照。历史月份不能重写原分配，可修正用户确认的存款；新月规划需重新测算。
- 首期主动跟进发生在进入助手或打开计划时；尚未提供离线定时推送、自动扣款或银行余额同步。微信真机及设备键盘仍需实际验收。
