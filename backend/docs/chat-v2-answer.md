# 聊聊花费 V2：可信回答与动态追问

2026-11-04，第 06 步交付。实现位于 `app/services/chat_v2_answer.py` 和 `chat_v2_suggestions.py`，复用[有限工具循环](chat-v2-loop.md)及[上下文持久化](chat-v2-context.md)。本步提供可调用的内部完整闭环，V2 路由、SSE 与小程序展示仍由第 07—09 步接入。

## 回答从哪里来

`AnswerServiceV2.run(conversation_id, SendMessageV2)` 先运行工具循环，再将其结果转为 `PreparedAnswerV2`，包含经过验证的 `AnswerPreviewV2`、上下文草稿、实际请求计数及原整轮期限。本服务不自动保存消息。

采用“模型决定查什么和重点、后端组织事实句”的方式：

- 模型草稿中的真实引用可以帮助选择本轮相关结果；自由文字不直接成为消费结论。单靠替换数字不能证明“失恋导致购物”“一定能省钱”等语义，因此这些推断不进入回答。
- 金额、笔数、日期、两期金额、差额、变化率及分类差额从本轮工具事实和对应卡片读取，显示实际范围，不用历史会话中同名的 `q1` 引用。
- 金额使用整数分格式化，比例使用整数基点与 Decimal，不引入浮点计算。负差额保留符号，收支分别展示，不把收入和支出相加或自动抵扣退款。
- 上期没有匹配记录时明确说明，不能据此断定真实消费增长；基期为零不生成增长率。分类差额明确为账单数值贡献，不写成生活事件或实际原因。
- 没有数据时只说明当前范围的记录情况，可建议查其他条件，不生成节省方案或承诺。本阶段没有预算、情景估算或预测，后续步骤不能将估算混入实际账单事实。

例如，当前筛选总额为 47501 分、笔数为 6 时，正文直接说明实际日期、合计 `¥475.01` 和 `6 笔`。查询明细时说明显示的是本页，统计覆盖全部匹配记录。数字均可对应返回的本轮 `factRefs`，不是模型自己编写的金额。

`render_fact_template` 校验 `{{q1.expense.total}}` 等占位符，检查本轮引用存在，拒绝额外阿拉伯数字、全角/兼容数字、金额及百分号、中文数值表达和残缺占位符；文字事实也不能作为数值注入的旁路。这个函数仅证明引用与数值的来源，不证明自由文字的语义，因此正式正文仍使用后端事实句。

草稿出现未验证数字、未知引用或过长内容时，舍弃草稿，返回后端事实说明，标记 `partial/missing`，不冒充已经完整生成。工具事实本身版本、来源、指标/单位不匹配或结构不完整时直接失败。相同筛选和收支的多次聚合如出现不同合计/笔数，返回 409 要求重查，避免把变化中的快照拼成严格归因。

## 怎样选择卡片

优先根据本轮问题和有效事实引用选取相关结果，最多三张卡片：

| 本轮结果 | 回答与卡片 |
| --- | --- |
| 当前范围简单汇总 | 先直接回答，可不附卡；仍返回本轮事实并生成追问 |
| 分类或日期分组 | 保留后端原始汇总/趋势卡，说明真实筛选范围 |
| 搜索或单笔查询 | 展示真实账单卡，原备注作为账单数据保留，不写成消费原因 |
| 两期比较 | 展示比较卡，按需附查到的明细，不强制追加无关汇总 |
| 需要澄清 | 使用后端的对象选择或条件补充提示，不输出消费结论，不硬凑追问 |

简单汇总仅在实际卡片筛选与候选上下文一致时省略卡片；范围不一致时保留卡片供核对。隐藏卡片时，普通追问使用保存轮次的上下文，不引用不存在的隐藏卡片。

## 动态追问与受控引用

追问由后端根据本轮结果生成，通常二至三条，最多三条；没有合适目标或需要澄清时允许更少，不生成无效账单操作来凑数量。`Suggestion` 的公开结构保持 `id/text/sourceTurnId/reference?`。

| 已有结果 | 可用追问 |
| --- | --- |
| 简单汇总 | 查看明细、按分类分开、比较前一等长区间 |
| 期间比较及真实分类差额 | 查看差额绝对值最大的分类明细、查看匹配账单 |
| 单笔明确账单 | 查看该账单，引用明确账单 ID |
| 比较后查到一笔明确账单 | 排除该笔后按原范围重新比较，保留原比较区间 |
| 带关键词的零结果 | 清空备注关键词重查；不自动扩大查询 |

普通卡片追问绑定当前消息 `sourceTurnId` 和真实卡片；涉及账单时还绑定实际展示的 ID。多笔账单不会随意选一笔并生成“这笔”的操作。差额分类仅从真实分类行选择，合并的“其余分组”或账户/记账人标签不会冒充分类。

`ContextStoreV2.validate_preview` 在返回前核对版本、建议文本、所属消息、来源卡片和账单访问；`save_success` 保存前再次核对，伪造来源或未展示账单不会落库。建议随 `result.payload.suggestions` 一起持久化，无新字段、表或迁移。

点击后的内部流程：

1. `resolve_suggestion` 只在当前账号、当前账本、同一会话的已保存轮次中查回建议 ID。
2. 请求文字必须与保存文字相同，来源轮次、引用卡片及账单必须仍然合法；未知 ID、篡改文字、跨账号/账本和删除/失权对象拒绝。
3. 后端按固定建议类型恢复来源范围，构造 `ContextPlanV2`，复用日期与筛选校验；用户可能已聊到其他日期，也不能误用新的范围解释旧建议。
4. 有明确账单的建议重新解析有效引用；新的工具查询读取当前账单，不复用旧金额。普通查账建议不会因为来源卡片中无关账单后来被删除而失效。
5. `ChatLoopV2` 使用这个已验证计划，跳过一次模型筛选规划，后续查询和结束决策照常计入限制。客户端不能凭建议 ID提交自定义工具或上下文。

这里的“排除”只改变分析筛选，不删除账单。只有建议随轮次保存后才能点击执行，流式未确认预览中的建议 ID 不构成可执行来源。第 07 步已通过 `save_turn` 保存明确部分消息，并清空其可执行建议、保留上一成功上下文；完整成功保存路径仍拒绝 `partial`，详见[V2 接口与流](chat-v2-api.md)。

## 期限、保存与接入

回答和建议生成不增加模型请求。`LoopOutcomeV2` 绑定原消息 ID、文字、建议 ID 和单调时钟 deadline；准备回答不能换消息或重新开始超时预算。准备阶段、预览核验和返回前继续复核版本及权限，失权、冲突、到期或取消不更新成功上下文。

服务内部调用示例：

```python
loop = ChatLoopV2(store, ChatModelV2(llm))
ready = await AnswerServiceV2(loop).run(conversation_id, message)
# 第 07 步在相同期限、会话锁、幂等及 SSE 生命周期中接入保存。
if ready.preview.completeness == "complete":
    async with asyncio.timeout_at(ready.deadline):
        turn = await store.save_success(ready.draft, message, ready.preview)
```

`done` 必须在保存成功后发送；不能把第 05 步的原始草稿直接发给客户端。V1 渲染、接口和前端不接入本模块。
