# 聊聊花费 V2 场景评测与真实联调

第 10 步使用固定虚构账单验证自然语言、工具、当前上下文和保存结果的一致性。不是以模型措辞与某句标准答案完全相同作为验收依据，也不使用用户的真实账单做测试。

## 可复用入口

场景在 `app/evaluations/chat_v2_cases.py`，执行器为 `app/evaluations/chat_v2.py`。包括十三类场景，每类三种不同表达，共三十九个独立样本；连续追问样本还会继续完成六轮。可信今天固定为 **2026-10-27**，评测实际执行日期单独记录，避免“上个月”“最近七天”随运行日期漂移。

在 `backend` 目录执行：

```powershell
$env:PYTHONIOENCODING='utf-8'
# 默认只列出清单，不读取连接配置，不发送模型请求。
.\.venv\Scripts\python.exe -m app.evaluations.chat_v2

# 明确启用真实开发库、Redis 与模型；会产生模型调用。
.\.venv\Scripts\python.exe -m app.evaluations.chat_v2 --live --variants 3 --workers 2

# 定向评测，不自动重试或更换协议/工具模式。
.\.venv\Scripts\python.exe -m app.evaluations.chat_v2 --live --cases recent_compare keyword_add --variants 1 --mode native --output ../output/chat-v2-evaluation/targeted.json
```

只允许 `development/test` 配置及 `keeping_accounts_dev` 数据库。每个表达建立独立的虚构用户、共享账本和不可见对照账本，所有数据库操作位于外层事务，模型等待前释放应用短事务，最终回滚并逐表确认不存在测试记录。Redis 使用运行专属前缀，仅清理确切的测试限流/锁键并确认不存在，不扫描或清空整个 Redis。测试分页密钥临时生成，不改 `.env`、生产开关、模型或部署。

报告默认写入本机忽略目录 `output/chat-v2-evaluation/`，逐样本保存结果。包括协议、工具模式、`gpt-6-luna`、`xhigh`、模型/工具调用次数、首个有效快照、每轮耗时和清理结果。HTTP 请求统计含上游返回的整数 token 用量；不据此猜测费用。固定虚构输入对应的结构化决策用于排查差异，**不保存 reasoning、encrypted_content、HTTP 原文、连接串或密钥**。

## 固定数据与检查依据

数据包含奶茶、咖啡、餐饮、耳机、两位记账人、退款收入、历史月份、已删除账单、未来账单和不可见账本。特意加入餐饮分类的“咖啡和面包”，用来发现把备注关键词错误地换成整个咖啡分类的问题。

- 2026-10-21 至 27 日支出：¥400.00，8 笔；退款收入 ¥50.00 单独统计。
- 上一期 2026-10-14 至 20 日支出：¥60.00，3 笔；两期差额 ¥340.00。
- 备注含奶茶：¥55.00，3 笔；追加咖啡后：¥95.00，5 笔；再排除“退款”备注：¥85.00，4 笔。
- 排除已展示的耳机账单：¥200.00，7 笔；小林记录的支出：¥90.00，2 笔。
- 咖啡茶饮分类：¥80.00，4 笔；对照无记录基期不生成增长率。
- 餐饮分类：¥120.00，3 笔；九月份餐饮/全部支出均为 ¥80.00，1 笔。

预期由独立 Python 筛选/计算产生，不复用 SQL 构造器或工具聚合。每次实际工具调用都核对全范围金额/笔数、分组金额/比例和明细 ID；随后核对最终回答事实、实际日期、比较范围、关键词、真实排除引用、记账人及保存的权威上下文。相同消息 ID 的再次发送必须重放原结果，不能新增模型调用或历史。

| 场景 | 重点 |
| --- | --- |
| 最近七天比较 | 包含今天的两个等长区间、差额、分类贡献 |
| 关键词扩展 | 保留奶茶并追加咖啡，按备注任意匹配，包含不同分类的咖啡备注 |
| 排除账单 | 从真实 SQL 生成并保存的单笔历史快照解析引用，不猜 ID |
| 按记账人 | 小林显示名映射到当前账本成员标识，不当成付款人 |
| 无数据 | 零金额/零笔数，不能编造记录或现实消费原因 |
| 零基期 | 本期金额正确，上期零记录不推算增长率 |
| 六轮追问 | 奶茶、追加咖啡、排除退款词、清空词、餐饮、比较，恢复全部轮次 |
| 模糊指代 | 没有可引用账单时澄清，不能擅选一笔 |
| 权限失效 | 模型调用前拒绝，不能返回零消费或泄露旧记录 |
| 工具失败 | 在真实规划后注入查询故障，不作为零结果成功保存 |
| 断连重试 | 真实查询完成后取消服务层 SSE 消费；核对未保存、锁释放、原 ID 重试及已保存 done 重放 |
| 旧会话恢复 | 保留 V1 原始回答；新建 V2 后继承旧月份/分类，续聊不覆盖旧历史 |
| 历史按月 | 九月份和“上个月”的查询，防止升级后按月能力退化 |

权限失效场景按设计不启动模型；工具故障和断连为明确的故障注入。历史准备使用真实 SQL 结果。除了这些受控故障和准备步骤，待测自然语言走真实模型、开发数据库和 Redis；不把故障注入说成上游服务自然发生故障。HTTP 鉴权/路由/SSE 集成另有 `test_chat_v2_api_integration.py`，与服务层真实模型评测分开记录。

## 联调发现与修复

1. 模型在最终草稿中复述“最近七天”等数值范围，被严格事实校验降为部分结果。现在要求最终草稿只选事实引用，日期、单位与正文仍由服务器生成；数值校验没有放宽。
2. “咖啡也算上”曾被规划为追加分类，查询却使用追加后的备注词，导致查询与保存条件不一致。加强条件编辑提示，并在完整回答保存前校验主统计与讨论条件一致；集合顺序不影响语义相等。单笔查看保持原讨论范围，部分结果继续不覆盖成功上下文。
3. 模型缺少将成员姓名映射到标识的依据。现在通过已鉴权账本提供受限的相关记账人目录，姓名仍按数据处理，不是指令；普通查询不发送成员目录或当前用户标识。成员目录超过五十人时明确标记截断，不能猜测未提供的身份。
4. 六轮追问中，规划器已清空关键词，执行器却受旧 `history.context` 影响而再次确认。现在规划器保留旧上下文用于修正，执行器只接收本轮权威 `currentContext`，历史问题/回答单独作为快照；三组六轮真实复测全部通过。
5. 一次开发连接中断导致旧评测池连接长时间等待。评测器增加数据库命令等待上限和池连接检查，断连测试同时等待工具结果与消费任务结束，避免工具尚未返回就无意义地等满期限。生产连接配置没有随评测修改。

应用内“数据与隐私”和分析入口说明同步说明按记账人查询所使用的信息。生产仍默认关闭 V2，未部署或上传。

### 速度与调用次数

协议为 `responses`。请求模型及恢复批次返回的模型标识均为 `gpt-6-luna`，请求保持 `xhigh`。本机真实配置仍为 `CHAT_V2_ENABLED=false`、默认工具模式 `structured`；评测中的原生模式和临时分页密钥只在测试进程显式覆盖，未改真实 `.env`。

最终通过样本的 **45 个已完成查账轮次**，排除权限/故障负向场景、澄清及缓存重放，统计如下：

| 指标 | 最小 | 中位数 | P95 | 最大 |
| --- | --- | --- | --- | --- |
| 首个已验证快照 | 39.0 秒 | 52.5 秒 | 81.3 秒 | 96.3 秒 |
| 整轮完成 | 44.0 秒 | 60.1 秒 | 87.2 秒 | 102.4 秒 |

首个快照指包含已验证事实的 `snapshot` 事件，不含状态或心跳；简单汇总的正文在后续 `delta` 展示，这不是单独测量的屏幕首字时间。整轮包含鉴权范围检查、数据库/Redis 往返、模型、校验和保存，样本来自本轮分批开发评测。

普通查账通常为三次模型请求和一次工具调用；个别比较先汇总再比较，为四次模型请求、两次工具调用。六轮样本各十八次模型请求、六次工具调用。断连样本包含一次有意中断的查询，合计五次模型请求、两次工具调用；完成后的同 ID 重放不再调用模型。权限失效在模型前拒绝，工具故障也不会生成零消费。

当前开发环境每轮中位约一分钟，仍有明显等待。本步保留既有模型与推理强度，后续性能工作先分别测量模型等待和数据库/Redis 往返，再评估参数调整。上述有限开发样本用于验收和发现问题，不作为生产成功率或时延承诺。
