# 聊聊花费 V2：前端状态与流处理

2026-11-05，第 08 步交付。对接[后端 V2 会话与 SSE](../../backend/docs/chat-v2-api.md)，在既有聊天页面上接入协议选择、类型校验、历史、卡片数据、部分结果及动态建议。后端开关和已发布小程序没有自动更新，本步没有部署或上传。

## 协议与范围

`store/chat.ts` 的 `protocol` 为 `unknown/v1/v2`，`ready` 表示已确认可使用当前账号和账本的会话。

1. 登录并连接账本后，请求 `/api/v1/assistant/v2/capabilities`。
2. 验证响应形状、支持版本及 `enabled`。只有明确关闭或能力接口 404 才选择 V1；网络、401/403、5xx、格式错误或不支持的启用版本均保留错误，不能偷偷改协议。
3. V2 创建传 `initialMonth`，列表只按当前账本读取，不按入口月份过滤；V1 保留自然月接口和旧结果展示。
4. 新请求一旦分配消息 ID，协议连同原文、建议 ID 一起固定。发送后的 404、失权或服务故障都不能自动改走 V1 重发。

V2 的入口月份只作为新会话默认值，改变入口月份不重置同账号、同账本的已有对话。顶部按 `contextV2.filters` 显示实际起止日期和收支类型；完整筛选、比较范围及来源保留在类型化上下文中。历史可以跨入口月份读取，旧协议仍检查会话月份一致。

V2 历史页另有“查看入口月份的旧版对话”入口，使用原 V1 历史接口保留完整旧统计卡，只读展示，不能直接发送 V2 消息。用户主动选择“基于此对话开始新版续聊”后，调用后端 legacy fork 并读取新会话，继承原筛选而不改写旧记录；响应丢失时复用原目标会话 ID 与入口月份，避免重复创建。这个显式旧版读取不改变已经协商的消息协议。

## 状态与确认

| 状态 | 行为 |
| --- | --- |
| 未完成能力/历史读取 | `ready=false`，保留错误，阻止发送 |
| 正在发送 | 固定 `pending`，禁止并发发送，预览与正式历史分开 |
| 收到快照/正文 | 替换完整预览或追加正文，仍不判定消息已保存 |
| 收到有效 `done` | 校验原消息 ID/文字，合并正式轮次、清空 pending/preview；保留完整性和缺失说明 |
| 断流、取消或错误 | 保留原 pending 和最后一个有效预览，显示未确认提示；重试不生成新编号 |
| `done + partial` | 是已保存消息，展示“部分完成”和 missing，不伪造完整结论或追问 |

V2 `snapshot` 整体替换正文、卡片、事实及建议，不能在上一份数组后追加。`delta` 必须建立在已验证的快照上，正文累计最多 2500 字符。`done` 完全覆盖预览；缓存重放可直接只有 status/done，不强制要求先出现快照。

重新读取对话时，只有找到了相同 ID 且原文一致的已保存轮次，才能清理 pending。未在最近一页找到原消息时继续保留原编号和预览，可安全重试；不能把一次成功的历史请求误当作本条消息已提交。

## 权威上下文与分页

V2 使用历史响应顶层 `context`，不从最后一条消息、部分结果或旧页结尾推导当前条件。翻页验证会话/账本、序号方向和消息唯一性，合并后保持升序。顶层更新时间较旧的响应不能覆盖已知较新的范围。

`done` 可能是此前消息的幂等重放，因此收到后还会读取当前会话的顶部状态，避免把另一设备的新筛选覆盖为旧消息中的上下文。如果这个刷新失败，正式结果依然保留，但暂时阻止继续发送，需重新读取确认范围；不会把已保存结果当作发送失败再生成一条消息。

其他设备新增超过一页消息时，旧本机缓存与最新页之间可能有序号缺口。此时先恢复连续的最新页，再从该页正常向前加载，避免将很早的单条缓存当作完整历史而丢失中间记录。

## 建议及卡片数据

`common/types/chat-v2.ts` 对齐后端筛选、上下文、事实、四类卡片、建议、预览、消息和历史类型，由既有 `types/chat.ts` 导出类型。`common/api/chat-v2-codec.ts` 对网络数据做运行时校验，包括协议版本、日期、UUID、整数及单位形状、卡片/事实唯一性、引用完整性、明细必需字段和完整性状态。

财务数字必须为 JavaScript 可安全表达的整数；超出安全整数范围时拒绝数据，不四舍五入冒充准确值。金额及基点显示使用整数分解，不在前端重新计算总额、差额或增长率。

第 08 步先提供基础只读卡片展示；第 09 步现已接入[专用结果卡、账单详情及阅读交互](chat-v2-cards.md)。旧结果仍使用原展示，游客继续使用明确标注的本地示例。聊天本身不会写入账单，编辑须进入既有表单确认。

动态追问只来自已保存的完整 V2 消息，预览或部分消息中的建议不能执行。点击时只用保存过的建议 ID 与原文，客户端不提交卡片、事实、身份、筛选或工具参数。`retry()` 始终复用 pending 中的消息 ID、正文、协议和建议 ID，不能把建议重试退化成一次新的自由提问。

## 切换、取消与传输

- 账号或账本切换、账号重新初始化时同步清理对话、范围、预览和建议，并取消活动流。
- 切换到“一句话记账”、页面隐藏或卸载时调用 `suspend()`，取消流但保留当前范围和未确认消息；重进相同范围仍可读取或按原编号重试。
- 每次生命周期变化推进 generation，迟到的能力、历史、分片或 done 都不能写回新范围。
- Ledger 的聊天 HTTP 请求绑定发起时的账号、账本和 token，响应到达后再次核对；不改变记账草稿和普通账单的独立状态。
- 微信继续使用分块 `uni.request`，H5 使用 fetch reader；共享 UTF-8/SSE 分帧逻辑，兼容中文/表情跨字节、CRLF 和多帧。错误及取消会终止连接，H5 结束后释放 reader 和计时器。

客户端取消只意味着本次不再确认保存；若服务器已经提交，后续读取或原 ID 重试仍可恢复。页面不会宣称取消必然撤销服务端已提交的消息。

未确认请求和预览保存在当前应用内存中，页面重进可恢复；应用进程被系统回收后，从云端历史恢复已保存轮次，不承诺恢复尚未保存的本机待发请求。
