# 消费体检判断原卡更新修复

2026-11-16，修复点击「可以调整、必要支出、一次性支出、判断不准确」后，原内容没有明确变化、消费卡片被下一项替换的问题。本次只修改前端，需要重新编译上传小程序，后端无需发布。

原先保存判断后立即重新拉取工作区和完整报告。新报告会排除必要、一次性及不准确项，并恢复普通排序，导致用户正在操作的消费被替换，智能分析的重点顺序丢失。

现在以服务端保存回包为准，按消费 key 更新原卡片的判断，保留本轮报告的卡片、排序和展开依据，在原位置显示「已选择」及后续处理说明。用户可直接切换四种判断；重复点击已选项不提交。必要、一次性及不准确项隐藏原削减建议和设置上限入口，同时移除草稿中的对应调整行动。重新主动分析时仍遵循后端排除规则。

移除判断及失败后的原请求重试均采用同一更新路径。保存失败保留原选择，回包判断与请求不一致时提示核对，不提前显示保存成功。

验证：

- `npm run check` 全部通过，存钱状态检查由 9 组增至 13 组，新增四种判断原卡更新、请求失败与原请求重试、移除标记、异常回包验证。
- H5 手机视窗使用虚构账单并拦截全部业务接口，实际点击四个选项。卡片数量及模型顺序保持一致，其他卡片的账单依据保持展开；四次切换只提交四次反馈，不重新请求报告，重复点击不提交。
- 模拟 503 保存失败后原选择保持，重试正文及请求 ID 一致，成功后更新原卡；移除判断恢复原卡未选状态。
- 微信小程序及 H5 构建通过；界面截图为 `output/playwright/savings-feedback-in-place.png`。尚未上传小程序或进行微信真机验收。

## 微信点击错位的补充修复

随后用户反馈：首项是「学习」，点击判断后被标记的却是下一项。前一轮 H5 点击检查没有覆盖微信事件绑定与原生画面更新之间的间隔，因此未发现这个问题。

在微信编译产物中复现：内层按钮只用 `classification` 作为 key，事件闭包捕获外层消费。微信运行时按事件序号和 key 复用处理器，列表重新排序时会先更新处理器，画面尚未完成更新时，旧按钮可能调用下一项的闭包。复现中画面为「学习」，提交的 `candidateKey` 却属于「餐饮」。

补充修改：按钮 key 同时包含消费编号和判断；按钮通过 `data-candidate-key`、`data-classification`、`data-source-month` 携带自身身份，统一事件处理器从 `currentTarget.dataset` 读取并验证，不再捕获外层消费对象。已切换月份或已被移除的消费按钮事件会被忽略。

新增 `scripts/check-savings-weixin.mjs`，执行实际微信编译产物及已安装微信运行时的 `vOn` 注册逻辑，使用虚构账单覆盖五组回归：首中末项各四种判断、原生画面保留旧顺序时点击学习、前项条件按钮消失导致事件序号变化、旧月份与已移除项、重复与非法选项。按钮数据及事件绑定直接从 WXML 和编译渲染结果读取。该检查已加入 `npm run build:mp-weixin`，属于编译产物回归，不等同于微信真机手势验收。

补充验证已通过：TypeScript 检查、`npm run check:chat`、微信编译产物五组检查、微信及 H5 构建；H5 四种实际点击和失败重试、移除判断也重新验证通过。本次未修改后端，未上传小程序。
